## Reflection

Part A gets total events and total failures per producer in one pass over `match_participants`. Two separate queries--one counting every row per match, one counting only contested or abandoned--would read the same table twice. For a large number of rows, that is a lot of extra work for the same answer, and the two runs could conflict if new events happen in between. One pass with `SUM(CASE WHEN …)` keeps one definition of failure in one place, which is what I would run on a schedule. Filtered queries are fine when I am exploring, but for a metric leadership might refresh often, I would rather not maintain two versions of the same grouping that can drift apart. Conditional aggregation also makes the SQL easier to read as one question with two columns, not two files that have to stay in sync.
